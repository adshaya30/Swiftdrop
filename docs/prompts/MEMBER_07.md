### PR B: consumers (FR-DEL-001, 010, 012; SRS 3.5)
Queue `delivery.events` with `EventConsumerSupport` and `ProcessedEvents`:
- `parcel.created` → insert the unassigned `deliveries` row (copy ids, owner, district and zone names, cities, `parcel_created_at`; status `CREATED`, sequence 1); idempotent.
- `parcel.status.changed` → update status, `status_sequence`, `terminal_at` for terminal statuses; **stale sequence (not greater than stored) is acknowledged and ignored** (this also covers updates already applied by #8's own action); a status event for an unknown parcel is a **retryable** error.
- `courier.changed` → upsert the `couriers` directory (name, vehicle, status). On status `DEACTIVATED` (**FR-DEL-010**) in **one transaction**: unassign that courier's `CREATED` deliveries (clear `courier_id` and `assigned_at`, close the open `delivery_assignments` rows with `unassigned_at`, write `delivery.unassigned` `{parcelId, unassignedAt, reason:"COURIER_DEACTIVATED"}` per parcel); never touch parcels already in progress.
- `processed_events` insert in the same transaction as the handling. Tests with Testcontainers PostgreSQL and RabbitMQ: idempotency (same event twice), stale and unknown-parcel behaviour, deactivation unassigns only CREATED and emits events, courier upsert.

### PR C: assignment and admin APIs (FR-DEL-002, 009, 011, 012; Flow 5; AT-17, 27)
All ADMIN only (others 403, unauthenticated 401, client tokens 403).
- **`POST /api/v1/admin/deliveries/{parcelId}/assign` `{courierId}`:** in one transaction take the pessimistic write lock on the `deliveries` row; unknown parcel or courier → 404; status not `CREATED` or courier not ACTIVE → 409 `PARCEL_NOT_ASSIGNABLE`; set `courier_id` and `assigned_at`, close the previous `delivery_assignments` row, insert the new one (`assigned_by` = admin id); write `delivery.assigned` `{parcelId, courierId, courierFirstName, assignedAt}` and an audit event (`DELIVERY_ASSIGNED`, entityType `DELIVERY`, details: courier ids only) in the same transaction. Assignment does **not** change the parcel status. Re-assigning to the same courier returns the current state without new rows. Response: the delivery info of the next endpoint.
- **`GET /api/v1/admin/deliveries`:** filters `assigned` (true/false), `status`, `courierId`, origin and destination district codes, creation date range (Asia/Colombo), `q` = tracking-number prefix; paginated; the unassigned queue (`assigned=false&status=CREATED`) is sorted oldest first, everything else newest first. **`GET /api/v1/admin/deliveries/{parcelId}`:** `{parcelId, trackingNumber, status, courier{id, fullName, vehicleType, vehicleNumber}?, assignedAt?, assignments[{courierId, courierName, assignedBy, assignedAt, unassignedAt}]}`.
